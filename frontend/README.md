# Веб-интерфейс ScheduleService

SPA для учебного отдела: ведём академические группы и преподавателей, просматриваем недельную сетку занятий. Задача [#37](https://github.com/akhtyamovpavel/BiGithubFlow2026/issues/37), ветка `feature/frontend-spa`.

## Локальный запуск

Используем Node.js 22.12 или новее и npm. Из корня репозитория запускаем бэкенд по основной инструкции проекта, затем фронтенд:

```bash
cd frontend
npm install
npm run dev
```

Открываем `http://localhost:5173`. Vite передаёт запросы `/api` и `/health` на `http://localhost:8000`. В локальной разработке отдельная настройка CORS не нужна. При ограничении системы на число файловых наблюдателей запускаем `CHOKIDAR_USEPOLLING=true npm run dev`.

Для воспроизводимой установки по `package-lock.json` используем `npm ci`. Дополнительные настройки копируем из `.env.example` в `.env.local`, затем перезапускаем Vite:

| Переменная | По умолчанию | Назначение |
| --- | --- | --- |
| `VITE_API_BASE_URL` | `/api/v1` | Базовый адрес API, без завершающего слеша. Можно задать полный URL. |
| `VITE_HEALTH_URL` | `/health/ready` на origin API | Проверяем готовность приложения и базы данных раз в 30 секунд. Для API под префиксом задаём полный путь явно. |
| `VITE_SCHEDULE_PATH` | `/lessons/` | Путь относительно базового адреса API. Например, `/schedule/groups/1`, если будущий endpoint возвращает массив `LessonRead`. |

Значения `VITE_*` входят в собранный JavaScript. Для отдельного домена API потребуется разрешить origin фронтенда на бэкенде. `npm run preview` только раздаёт сборку, поэтому прокси для API в таком режиме настраиваем отдельно.

## Экраны и контракт API

- `/groups`: создаём, редактируем и удаляем группы. Фильтруем по точному названию факультета, курсу и активности.
- `/teachers`: ведём преподавателей, фильтруем по точному названию кафедры и активности.
- `/classrooms`: ведём аудитории (корпус, номер, вместимость, проектор, компьютеры, статус активности).
- `/subjects`: ведём учебные дисциплины (название, код курса, описание).
- `/schedule`: просматриваем Пн–Сб, пары 1–6. Фильтруем по группе, преподавателю, аудитории и чётности, планируем новые занятия с защитой от коллизий (`409 Conflict`), ищем свободные аудитории по слоту и минимальной вместимости, скачиваем расписание в форматах `.ics` и `.csv`.

Типы в `src/lib/models.ts` соответствуют схемам `GroupRead`, `TeacherRead`, `LessonRead` и `ReadinessResponse` из `src/schedule_service/schemas/`. Справочники используют коллекции с завершающим слешем: `GET/POST /api/v1/groups/`, `GET/POST /api/v1/teachers/`. Для записи используем `PUT/DELETE /api/v1/{resource}/{id}`. Списки API возвращаются массивами без общего количества записей. Для каждой страницы запрашиваем 11 записей, показываем 10 и определяем наличие следующей страницы по дополнительной записи.

Обрабатываем сетевые ошибки и ответы 404, 409, 422, 5xx. В формах показываем ошибки конкретных полей, при удалении сохраняем подтверждение открытым до успешного ответа. Закрытие формы во время сохранения заблокировано. Таймаут запроса составляет 15 секунд, при переходе между экранами отменяем незавершённые запросы чтения.

API расписания пока отсутствует. Только ответы 404 и 501 включают заметно обозначенный демонстрационный режим с вымышленными занятиями из `src/lib/demo-schedule.ts`. Пустой ответ 200 остаётся пустым расписанием. Ошибки сети и сервера показываются с кнопкой повтора. CRUD справочников всегда обращается к настоящему API.

Будущий endpoint расписания должен возвращать JSON-массив `LessonRead` с вложенными объектами `subject`, `teacher`, `group`, `classroom`, `time_slot`. Для размещения занятия обязателен `time_slot`; неполные записи и занятия за пределами Пн–Сб, 1–6 учитываем в сообщении над сеткой. Пагинацию будущего API расписания добавляем после согласования его контракта. Сетка показывает шаблон недели, а не календарный диапазон. Создание и изменение занятий в задачу #37 не входят.

## Проверки и сквозные E2E-тесты

```bash
npm run lint
npm run typecheck
npm run build
npx playwright test
```

Сквозные браузерные E2E-тесты находятся в `frontend/e2e/*.spec.ts` и запускаются через `npx playwright test` (базовый адрес `http://localhost:8080`, проект `chromium`, режим `headless: false`, `trace: 'on-first-retry'`, снятие скриншотов при падении) против поднятого Docker Compose стека с демонстрационными данными (`docker compose exec -T app python -m scripts.seed_demo_data`).

## Docker

Из корня проекта запускаем приложение, PostgreSQL и фронтенд:

```bash
docker compose up --build
```

Открываем `http://localhost:8080`. Все три сервиса описаны в основном `docker-compose.yml`. Фронтенд запускается после успешной проверки готовности API, а API ждёт готовности PostgreSQL. Сборка проходит в Node.js, готовые файлы раздаёт Nginx. Он направляет `/api/` и `/health` в сервис `app:8000`, поддерживает прямое открытие SPA-маршрутов и обновление страницы. Браузер и API работают через один origin.

Можно собрать образ отдельно:

```bash
docker build -t schedule-frontend frontend
docker run --rm -p 8080:80 --add-host=host.docker.internal:host-gateway -e BACKEND_URL=http://host.docker.internal:8000 schedule-frontend
```

Для отдельного запуска бэкенд должен принимать подключения со стороны контейнера. `BACKEND_URL` задаётся при запуске Nginx, без завершающего слеша. Переменные `VITE_*` передаём при сборке через `--build-arg`. В образе по умолчанию используются `/api/v1`, `/health/ready` и `/lessons/`.
